# app515 Music Note V2 rollback safety — Draft policy (2026-10-28)

**Scope:** SORIDRAW PR #512, new canonical `user_structures/{uid}/folder_state/v2` for updated browsers; legacy `user_structures/{uid}` remains readable/writable by old browsers. No deployment is authorized by this document.

## Non-negotiable compatibility rule
After app515 first reaches PREVIEW, **never deploy or roll back any environment to an app that reads only `user_structures/{uid}`**. Legacy app versions cannot see newer V2 folder changes, so an old binary makes folders seem lost even though V2 originals remain intact. This rule protects PREVIEW, TEST and PRODUCTION and all 3 environments share the real user data. It also applies to manual Vercel/Firebase deployment/alias changes, emergency reverts and mobile cached old tabs.

Use only an independently audited **V2-aware build** as the rollback baseline. Preserve all V2 documents, legacy originals, the 60-second pending queues and RTDB signals unchanged. **Never mirror V2 automatically back to the legacy parent; never clear caches, delete folders, or mass-backfill user data.**

- `.github/workflows/firebase-hosting-custom-preview.yml`: before any PREVIEW Firebase rules/Hosting deployment, load current `origin/preview`'s rollback guard even if a historical `target_sha` was checked out. Prevent PREVIEW old-browser Hosting releases after V2 code is adopted.

## Exact Firebase backend target and read-only readiness checks

**Release-blocking environment split:** `src/firebase.js` initializes the user Firestore/Auth SDK in project `soridraw-app-866a5`. The PREVIEW Hosting workflow deploys to Firebase project `soridraw`, which is **not** the same default deployment target. Never infer a shared Firestore/Functions deployment from `FIREBASE_PROJECT=soridraw` or a successful Hosting run. All three app environments use the shared user project.

1. **Read-only actual-state inventory first:** independently identify the active Firestore Rules release and deployed `syncMusicNoteStructureVersion` + proposed `syncMusicNoteFolderStateV2Version` Functions **for the shared Firestore project `soridraw-app-866a5`**, including the Functions event source project, target region `asia-northeast3`, service identity, permissions, runtime, and function names. Do not query a user's folders as a substitute for Rules/Functions inventory.
2. **Fail closed for project mismatch:** before any future authorized backend rollout, require explicit verified target project `soridraw-app-866a5`. A default `firebase deploy` inferred from the Hosting project `soridraw` is prohibited. Capture immutable backup/version metadata for the **currently deployed shared Rules and Functions**, and separately authorize the exact Rules + one named Function change.
3. **Pre-stage Rules, not client:** independent owner-only emulator verification of the additive `user_structures/{uid}/folder_state/v2` get/create/update and denied list/delete/cross-user writes; existing parent `user_structures/{uid}` legacy owner writes must still succeed. On separately approved activation, confirm the effective **shared Firestore Rules** match the approved additive change, with unrelated Rules byte/semantic behavior protected.
4. **Next, stage the one trigger:** build `functions/src/index.ts` through the existing `securedIndex.ts` generation path, then separately deploy only `syncMusicNoteFolderStateV2Version` to the confirmed shared project and region. Verify trigger name, active event-source project, writes `users/{uid}.syncVersions.musicNoteStructure` on **changed V2 folder content only**, and does not repeatedly advance revision when content is unchanged. A failed trigger is an unsolved cross-device convergence risk, not proof of V2 loss. Do not replace unrelated Functions.
5. **Only afterward consider client rollout**, contingent on separate director PREVIEW approval. Confirm source on `main` protects PREVIEW manual dispatch and both TEST/PRODUCTION auto-rollbacks. A failed Rules/Function activation means **no V2 app exposure**. PROD/TEST promotion requires separate later approvals.
6. **Cost is end-to-end, not merely direct document W1:** an ordinary new V2 edit uses a canonical V2 transaction (normally R1/W1, bootstrap may add a legacy R1), plus a successful Function invocation and its user sync-version transaction (typically another user R1/W1), plus RTDB transport traffic. Cold canonical refresh is R2 (parent+V2); healthy verified warm is R0; no-change folder write W0. Emulator/VM counters are not billed-real usage; log actual reads/writes/invocations during separately approved QA before any 100k-user projection.

## Mixed old-PC/new-mobile acceptance gates (NOT yet performed on real devices)

Use a dedicated, signed-in QA account and independently approved controlled edits; do not change the user's original account, clear old Chrome/mobile caches, restore missing songs, or force migrations. Record only sanitized IDs, pass/fail and billed counters.

- Older PC tab: retains parent `user_structures/{uid}` writes and its existing 60-second final-state behavior. A newer mobile saves **only** `folder_state/v2`, and neither original changes the other's canonical document. Repeat order A→B and B→A, including a PC delayed edit after modern ACK and Functions archive failure.
- Second newer PC and mobile: V2 reads agree after the actual trigger/profile signal; same-mode overlapping edit fails closed (pending + visible unconfirmed, no silent overwrite). RTDB preview is immediate but **never** mistaken for a Firestore ACK. Delayed/cross-order notifications converge to V2.
- My Note and Shared Note individually: old top-level `myNoteFolders`/`sharedNoteFolders` first migration preserves both, unchanged W0, 60-second batch, folder deletion/song membership guards, manual legacy/V2 compare and selected restore, no auto-restore.
- Offline, quota-full, app restart and slow ACK: pending saved or clearly warned about memory-only risk; once online/auth restored, no lost pending or newer overwrite. Actual cold R2, warm R0, per-edit direct W1 plus Function user W1, and recovery listing R1/explicit older R10 counted by documents returned.
- Three real device sessions: original PC, newer mobile, newer PC. Same authenticated UID, exact saved-song IDs and original prompts/lyrics/hearts protected. Original reported missing historical favorites remain **UNKNOWN** until a separate exact-ID authenticated read-only check; no title-wide query, re-save, or restoration without separate approval.
- **Fail if any item is unverified:** no PREVIEW deployment merely because source, emulator, GitHub CI or independent source audit passed. Legacy↔legacy writes remain a known pre-existing limit; manual out-of-band Hosting deploys and older cached clients require operational control.

## Mandatory activation / staged rollout (separate director approval)
1. Confirm CI + independent audit + read-only authenticated PC/mobile mixed-version evidence and exact release SHA; verify real database documents without editing or deleting user data. Existing logged-in old clients remain a supported read/write hazard for the old branch.
2. Verify and apply V2 owner Rules and `syncMusicNoteFolderStateV2Version` trigger **before** exposing the new app UI; confirm the trigger/Rules in each shared environment. Stop if mismatched. Check old parent data is still accessible and not force-changed.
3. Deploy only a verified V2-aware PREVIEW candidate after explicit director instruction. Verify first migration, old-PC delayed writes, old/new folder reconciliation, quota, 60-second W1, R2 on genuine confirmation and warm R0 with actual login. Then require separate TEST and PRODUCTION approvals.
4. Record exact V2-capable fallback SHA + hosting release ID before advancing environments. Roll back only to this or a newer V2-capable verified build; never to a pre-V2 binary. If no safe fallback exists, **freeze promotion** and fix forward. A failed deployment must not be 'repaired' by copying V2 content into the legacy doc.

## Limits
- The source floor cannot guarantee old-vs-old legacy writes; legacy clients lack CAS baselines.
- The controller does not deploy Firebase Functions/Rules. Use separately authorized exact-sha staging and independent checks, not this workflow's Hosting-only success as proof.
- No physical PC/mobile testing, live billing verification, cloud-environment activation or data migration is performed by merging this policy.
