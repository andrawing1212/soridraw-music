# SORIDRAW 디렉터 작업 계약 · 일일 루틴

적용: 모든 SORIDRAW 개발 채팅. 이 문서는 프로젝트 공통 지침 및 `AGENTS.md`를 보조한다. **역할 분담·특정 모델·에이전트 지정 규칙은 두지 않는다.**

## 1. 디렉터가 원하는 결과

- 합의한 기능은 누락 없이 실제로 완성한다. 코드 검사·GitHub 저장만으로 실사용 완료라고 말하지 않는다.
- 네가 이미 확인할 수 있는 정보를 사용자에게 반복해서 요구하지 않는다. 현재 지시가 과거 문서·작업 스냅샷보다 우선한다.
- 숨은 데이터 위험과 비용을 먼저 판단하되, 개발보다 절차·문서·감사가 커지게 만들지 않는다.
- 기존 정상 UI, Music Note/Library 로컬 즉시 반영·묶음 저장, Studio 하트, PC↔모바일 동기화, 사용자 원본과 서버 비용을 보호한다.
- 확인된 사실·추정·미확인을 구분한다. 거짓 성공 보고, 근거 없는 진행률, 실제로 지원하지 않는 버튼/도구의 가능 주장 금지.

## 2. 한 작업을 끝내는 방식

**작업공간에서 충분히 수정 → 테스트 → 실패하면 같은 자리에서 다시 수정 → 테스트 통과 → 의미 있는 한 덩어리가 끝났을 때 커밋 → 필요하면 PR → 승인된 경우 배포.**

- 시작 시 사용자에게 필요한 최종 동작, 전체 체크 항목, 변경 범위, 보호선, 합격 기준을 짧게 공유한다.
- 승인받은 범위 안에서는 확인·계획·수정·검사·실패 수정까지 한 번에 수행한다. 작은 단계마다 승인이나 GitHub 저장을 반복하지 않는다.
- 테스트 실패는 같은 작업공간에서 원인을 좁혀 고친다. 통과했던 검사를 무의미하게 다시 돌리지 않는다.
- 의미 있는 완료점에서만 GitHub에 저장한다. 실제 유실 위험이 큰 장기 작업에만 복구용 중간 커밋을 허용한다.
- 보호 브랜치·검토가 요구할 때만 PR을 만든다. 같은 기능을 app 번호나 PR로 쪼개지 않는다.
- 사용자 원본, 인증·권한, 공유 Writer, 파괴적 데이터 구조 변경처럼 복구가 어려운 위험에만 필요한 깊이의 독립 검증을 실시한다. 구현자가 자신의 작업을 독립 검증했다고 보고하지 않는다.

## 3. 채팅을 바꿔도 이어지는 기준

- 새 채팅에서는 사용자에게 지난 작업을 다시 설명시키지 않는다.
- 현재 사용자 지시 → 승인 목표 → 실제 GitHub `preview` HEAD·열린 작업 PR → 이번 작업에 필요한 AGENTS/CURRENT/NEXT 부분만 확인한다.
- 오래된 지시·기록·PASS를 새 승인으로 간주하지 않는다. 다른 채팅의 미저장 임시 파일을 볼 수 있다고 주장하지 않는다.
- 아래 새 채팅 시작 문장을 권장하지만, 같은 공통 지침을 매번 장문으로 붙이게 하지 않는다.

> SORIDRAW 개발방 이어가기. GitHub `andrawing1212/soridraw-music`의 최신 `preview`와 진행 중인 작업을 확인하고, 이전에 승인된 미완료 작업부터 이어가. 프로젝트 지침대로 확인·계획·수정·필수 검사를 한 흐름으로 끝내고, 의미 있는 완료점에서만 GitHub에 저장해. 역할 분담·모델 지정·반복 감사·불필요한 새 PR은 하지 마. 새 작업·병합·배포는 승인받고, 결과와 실제 미검증 부분을 간단히 알려줘.

## 4. 비용·데이터·배포 승인

- PREVIEW `preview.soridraw.com`, TEST `test.soridraw.com`, PRODUCTION `soridraw.com`. 사용자 원본은 환경 간 공유되므로 대량 삭제·변환·백필·캐시 초기화 금지.
- 페이지 이동·업데이트만으로 불필요한 DB 읽기·쓰기·전체 스캔을 발생시키지 않는다. 실제로 변한 항목만 처리한다.
- 일반 '프리뷰 수정'은 개발·검사·의미 있는 GitHub 저장까지이며 **자동 배포하지 않는다**.
- PREVIEW 배포는 명시된 경우에만, TEST·PRODUCTION 승격은 별도로 승인받는다. PR 병합이나 공유 Rules/Worker 변경도 승인 범위를 확인한다.
- 실제 PC·모바일 확인은 배포 후 수행 가능한 범위에서 검증하고, 확인하지 못했으면 미확인이라고 말한다.

## 5. 보고와 다음 승인

- 작업 시작: 이번 목표·범위·보호선. 작업 중: 중요한 완료·실제 막힘. 작업 종료: 완료/미완료·SHA(있을 때)·검사·감사·배포·PC/모바일·위험.
- 사소한 단계마다 표·체크리스트·퍼센트를 갱신하거나 보고를 강요하지 않는다. 같은 내용을 반복하지 않는다.
- 현재 승인된 작업이 완료되면 다음 독립 작업 하나만 제안하고 실제 사용자 승인을 기다린다.
- 지원 환경에서는 질문 바로 아래 **실제 작동하는 작은 둥근 YES / NO / 기타(글쓰기)** 버튼 3개를 가로 배치한다. 지원하지 않으면 불가능함을 알리고 가짜 버튼을 만들지 않는다.
- YES는 질문에 담긴 범위만 승인한다. NO면 중단한다. 기타는 새 지시를 받는다. 새 독립 개발·PR 병합·배포·사용자 데이터 변경을 암묵적으로 승인받았다고 간주하지 않는다.

## 6. 매일의 간결한 루틴

- 시작: GitHub의 실제 현재 상태 → 승인된 미완료 작업 → 긴급 문제 → 가장 중요한 일 하나.
- 진행: 작업공간 수정·필수 검사·실패 수정 완료 → 의미 있는 단위 저장 → 명시 승인된 경우 배포·실사용 확인.
- 종료: 사실에 근거한 완료·미완료·위험 → 다음 작업 하나 제안. 필요 없으면 새로운 기록·검사를 만들지 않는다.
- 자동 예약은 계획·알림이지 임의 코드 변경·배포 실행이 아니다.

**최종 목표: 사용자가 반복 설명·작업자 관리를 하지 않아도 실제 앱이 안전하게 완성되는 것.**
