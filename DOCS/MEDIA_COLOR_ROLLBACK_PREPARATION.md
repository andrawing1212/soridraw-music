## Eventual authoritative color projection design (NOT LIVE)

New isolated pure function `planCanonicalColorVersionTransition` supports per-document version fencing using **server-attested Firestore `updateTime`**. A future authorized writer may apply only an exact-UID/exact-ID canonical color change whose Firestore updateTime is *newer* than the R2 row's already applied source updateTime. It must use journal CAS and retry using the latest R2 version; explicit per-index `null` and removal markers are authoritative. An old event received after a newer one is rejected. Existing R2 color resets without a proven source-version remain untouched. Tests prove ordering for out-of-order events and clear→reselect. The function is currently **pure and not invoked by live Worker paths**, and the R2 source-version watermark is not yet stored by the catalog. No client can send an unauthenticated timestamp as authority.

**Crucial remaining implementation blocker:** Source-version comparison alone cannot guarantee an update is ever delivered. A fully durable design needs a narrow *at-least-once canonical change publisher/outbox* for color mutations only, plus a compatible color-version watermark in the shared R2 journal and all three active Writers. The existing local-on-exit Library color update and Music Note 60-second coalescing must be preserved. Any outbox or Firestore trigger impacts shared resources/costs and needs separate explicit approval and independently audited rollback. Do not add an automatic Firestore collection scan, whole-catalog reconstruction or per-page extra reads. Until every prerequisite is met, the read-only preview stays the only route.

A reserved server-only `__colorSourceUpdateTime` watermark in the trusted R2 row prevents reverse delivery from replacing a newer explicit color/null reset. ## Color-only durable outbox cost/remediation candidate (2026-11-03, NO DEPLOY)

The prior two **collection-wide** `onDocumentWritten(favorites/*)` and `onDocumentWritten(suno_tracks/...)` color triggers are **removed from the Firebase export surface**. They would invoke on all document changes even when no color changed. The opt-in browser transport (`VITE_COLOR_CATALOG_OUTBOX_V1=1`) instead uses one authenticated/App-Check-protected regional callable for **explicit color saves only**. With that flag absent, original Music Note and Library storage paths remain unchanged. Do not activate the new client flag until the server and Worker are independently released and verified.

For an actual color save the callable updates the exact owned canonical document and a deterministic per-UID/kind/document server-only `color_catalog_outbox` record in the same Firestore transaction. No Firestore Rules change and no browser write permission to the outbox. No-op unchanged color writes W0. After the transaction commits, the callable makes one best-effort signed Cloudflare delivery. On failure the outbox is retained. A bounded, gated 15-minute scheduler queries due outbox rows (`orderBy(nextAttemptAt).limit(80)`) and retries with backoff, without an expiration deadline. A successful Worker acknowledgement deletes only its own outbox generation in a transaction; a late ACK never deletes a newer pending color. There is no collection scan or page-entry work. Scheduler invocations and its empty indexed query remain nonzero even when idle *if activated*.

Cost tradeoff: this is **not zero-cost**. Each real changed color typically requires canonical R1/W1 plus outbox W1, two exact document reads during delivery, R2 sync R2/W1 and one outbox ACK W1 (approximately Firestore R4/W3 per color under normal no-conflict operation; retries add more). This trades high-volume all-document event invocations for color-only calls and durable retries. The full monthly cost is unproven; do not claim this is cheaper until actual canonical mutation rates and usage-tier prices are compared. One user song may generate many color edits but the existing on-exit local coalescing must remain. Old clients still using direct Firestore write cannot produce an outbox record; they require explicit release compatibility treatment.

**NO-GO remains:** neither source nor default feature flags deploy this pipeline.
