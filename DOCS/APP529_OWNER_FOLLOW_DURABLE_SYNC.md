# APP529 — durable owner follower sync source candidate (OFF / NO-GO live)

2026-11-09 approved developer scope: finish code, necessary isolated tests and preview-safe code release only. **No shared Worker, Functions, RTDB Rules, D1/R2 schema or user data change is authorized by this artifact.** Source PR #914 remains draft. The preceding client-only APP527/528 fix must be preserved.

## Architecture decision

- D1 `profile_stats.follower_count` is committed-count authority for the existing legacy writer. A D1 **AFTER UPDATE OF follower_count** trigger writes one coalesced owner outbox row into the **same SQLite transaction** only when the number actually changes. No second pre-state or materialized-profile GET is required. Control table defaults `enabled=0`. Rolling back or failing the outbox insert also rolls back the count change in the tested SQLite transaction.
- The per-owner `revision` increases in the committed transaction and is preserved as one durable row per owner. The server HMAC payload includes `revision, ownerUid, followerCount, updatedAt, at`. No browser-provided count, random request ID or delivery timestamp is used as the canonical ordering key.
- Worker source-only fast path processes at most 12 due records after an accepted mutation. A separate *unconfigured* `soridraw-owner-follow-retry-529` retry cron is required for crash recovery. Failed sends are saved with capped backoff, at most 8 attempts, and a durable `dead_at` hold for manual replay. Duplicate attempts may be sent; Firebase Admin transaction compares the owner's D1 revision and ACKs old/duplicate deliveries without changing A.
- A listens only to `userSync/{A}/exploreFollowerOwner529` when its own profile is visible. A signed canonical count is applied locally without an extra public R2/D1 GET. Retained RTDB scalars repair a stale cache, and older sequence values are ignored. Only A's followers-list cache is invalidated when a confirmed signal arrives. The existing 30-second actor batch and APP527/528 120-second explicit fallback are preserved.

### APP529 bounded-storage improvement
The outbox is keyed by `owner_uid` in this revised candidate (one row per owner), not one row per mutation. A changed count increments `revision` inside the canonical D1 transaction and replaces that owner's pending value. Only the latest count must arrive; intermediate transitions are superseded. The webhook applies a signed revision only if newer than the owner's stored RTDB revision. ACK and failed-attempt updates are CAS-filtered by owner and revision so an old in-flight reply cannot mark a new value as delivered. There is no periodic row deletion/retention job and no unbounded per-follow event log. This *still* costs an additional D1 W1 when a count changes and another W1 on successful delivery; Isolated Cloudflare D1 physical metering completed on 2026-11-09 (below); shared-production billing remains unmeasured.


### Economic and correctness proof refinement
Per-owner pending row is a **last-state projection**, not an append-only ledger. An always-active one-minute rescue cron would add a small global D1 read even without changed users, so its physical cost also requires measurement. Source OFF + user visits add D1 R0/W0. A new confirmed follower count writes one coalesced D1 outbox UPSERT (isolated count-changing UPDATE physical W3 total versus W1 without APP529, i.e. W2 added), and one CAS ACK after successful remote delivery. Failed calls update retry metadata in that same owner row; 8 failures hold `dead_at` for administrator replay. Owner row and version must not be deleted (order fence). This bounds storage by distinct owner UIDs, eliminating unlimited event-row growth and periodic retention DELETE. Different writers sharing D1 cannot be separated by this schema; shared activation is not approved. A 120-second popup cache fallback is preserved until real A/B and R2 consistency are demonstrated.


## Bounded recovery of 8-attempt dead hold (no automatic production access)
An isolated administrator must first read only `owner_uid,revision,attempts,dead_at,acked_revision` for the held row; no customer data or follower lists are needed. After verifying the remote signing/config issue is repaired and the **exact owner+revision** is still pending, an approved owner-specific UPDATE can set `attempts=0,next_attempt_at=0,dead_at=0` with `WHERE owner_uid=? AND revision=? AND acked_revision<revision AND dead_at>0`. Never reset all owners or delete the row (which would lose the monotonic ordering fence). `OWNER_FOLLOW_DELIVERY_DEAD_HOLD_REQUIRES_ADMIN_REPLAY` provides a generic log signal without logging UID or secrets. This is a future operating procedure, not authority to touch shared D1 today.

## 2026-11-09 — APP532 Auth-incarnation alternative (NO deleted UID tombstone; source-only)

**Scope of approved work:** evaluate the APP531 unbounded retired-UID journal and actual Firebase Auth deletion/recreation contract, preserve isolated D1 normal changed-follow W2 and ordered delivery, build/test a bounded alternative. ### Actual Firebase deletion contract (confirmed in `functions/src/index.ts` on `preview`)
The existing `adminDeleteUserAccount` callable checks an admin caller and target, marks Firestore account status banned, revokes tokens and deletes the Firebase **Auth** user, deletes personal API key and request-guard docs, then marks the Firestore user `authDeleted` with `adminDeletionContentPolicy: 'retain-user-content'`. It is not yet wired to APP532.

### Safer non-retention candidate
1. New `cloudflare/explore-worker/candidates/532-owner-auth-epoch-no-tombstone.sql` is an **alternative** built from APP530 shared base *before* APP531 retirement-table DDL, plus exactly one `profile_stats.owner_follow_auth_epoch_532` text column. It uses the existing APP530 due-index. **Do not install this on a shared database or run it on top of APP531.** No per-deleted-UID table exists in this candidate.
2. A trusted, server-controlled Auth incarnation epoch is a fresh cryptographically random 128-bit ID, issued **once per Auth account incarnation** and stored in its protected Firebase Auth custom claim `soridrawFollowEpoch532` plus D1 canonical owner row. D1 Writer source must require that same epoch on each count change. Missing/mismatched epochs **fail closed**, without any new D1 work on idle/view. The generation-enrollment/admin custom-claim provisioning is **not implemented or authorized**.
3. `cloudflare/explore-worker/runtime/owner-follow-auth-epoch-532.mjs` is a **compiler OFF** source module. The new atomic Writer remains R1/W2 on the synthetic D1; a changed-only operation includes `WHERE ... AND owner_follow_auth_epoch_532=?`. Indexed batch draining, all ACK CAS and failed-delivery CAS include **UID + Auth epoch + revision**. This addresses a deletion/recreation race where a stale ACK and a new user otherwise both have revision 1.
4. The future Functions recipient would require the existing signed/HMAC payload check **and** a trusted Firebase Admin `getUser(uid)` on each delivered event to compare the protected custom claim to the signed `authEpoch` value; deleted Auth users and old generations must cause **no RTDB write**. A valid *new* incarnation may start its marker at revision 1 regardless of an earlier incarnation's retained marker, but it may do so **only after Auth verification**. No live Function or RTDB listener has been modified to do this. A Firebase Auth read per received event introduces new unmeasured network/latency/cost.
5. Full D1 row deletion is a **separate future data-erasure workflow**: it must cancel outstanding writers, remove RTDB and other personally identifying state and coordinate the active Auth identity. With an Auth generation gate, no indefinitely retained D1 UID tombstone is necessary for stale-event rejection, but D1 row deletion **alone is not a full privacy erase** (SQLite backups, Auth logs, Firestore/R2 and cached data are not covered by this test). Do not add TTL to APP531 or enable both candidates.

### Findings and correctness fixes
1. Firebase RTDB rule `auth.token.epoch === data.child('authEpoch').val()` alone **incorrectly allowed an absent-claim user to read an absent marker** because both sides can be null. The emulator-only Rule now additionally requires **claim exists AND data.exists()**. The shared Rules file has NOT been modified.
2. Firebase RTDB JavaScript `transaction()` can call its updater first with a cold local `null`; immediately returning `undefined` aborts the deletion without reading the authoritative server row. `deleteMarkerIfGeneration533` now reads the marker first and uses the server-side transaction retry/hash to delete **only the matching generation**. This fix passed the actual emulator test, including old cleanup racing with newly recreated identity.
3. Firebase Auth `metadata.creationTime` can be **equal for distinct account incarnations** (observed in emulator). APP533 therefore treats a same-time, different-epoch marker as **fail-closed**, never a justified overwrite. The owner must be explicitly deleted/cleared before re-enrolling. Safe live recovery for same-time ties is not yet proven.

### Hard release blockers — NO-GO
1. Existing `adminDeleteUserAccount` in `functions/src/index.ts` **deletes Firebase Auth user but deliberately preserves user content**, and does not coordinate APP532 owner-marker cleanup or D1. The emulator exercises only the Auth aspect and isolated marker; it does not run the production callable, preserve/erase Firestore data, or alter the existing contract.
