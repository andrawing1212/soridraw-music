# SORIDRAW 디렉터 작업 계약 · 실행 체크리스트 · 일일 루틴

기록일: 2026-10-27 KST. 적용: SORIDRAW의 모든 ChatGPT 개발방/감사방, Codex, Work.
목적: 사용자에게 반복 설명·판단·작업자 관리를 떠넘기지 않고, 합의한 기능을 안전하고 효율적으로 **끝까지** 완성한다.
우선순위: 현재 사용자 명시 지시 > 해당 작업에서 마지막으로 합의된 범위·합격선 > GitHub 실제 상태 > 본 문서. 본 문서가 사용자 승인 없는 배포·위험 변경을 허가하지는 않는다.

## 1. 디렉터의 고정 요구 — 무슨 일을 해야 하는가

1. **결과 중심:** 개발 설명보다 사용자 눈에 보이는 실제 기능, 정상 작동, 완료 증거를 우선한다. 전문용어 대신 짧고 쉬운 한국어로 보고한다.
2. **합의한 기능 전부 구현:** 기능을 시작하기 전 요구 동작을 스스로 분석해 제안하고 승인을 받았다면, **어렵거나 시간이 걸린다는 이유로 일부를 임의로 생략하지 않는다.** 합의 사항 A/B/C 중 A만 해놓고 완료라고 말하는 행동 금지.
3. **기준 유지:** 구현 중 방식 변경·기능 제외가 필요하면 먼저 '원래 합의 / 바꾸려는 부분 / 포기되는 동작·위험'을 보여 주고 승인을 받는다. 사용자 승인 없이 더 편한 방법으로 목표를 바꾸지 않는다.
4. **작업 지시 한 번에:** 같은 일에 장문·단문을 번갈아 제시하거나 매번 '이것이 최종'이라고 번복하지 않는다. 기존 명령문은 유지하고 필요한 변경 사항만 짧게 추가한다.
5. **시간·사용량 관리:** 재분석·중복 전체 검사·불필요한 고비용 감사로 사용량을 소진하지 않는다. 로컬에서 작업을 끝내고 GitHub 저장 전에 중단되는 상황을 막는다.
6. **정상 기능 보호:** UI·색·배치·반응형·기존 동작, Music Note/Library 로컬 즉시 표시와 묶음 저장, Studio 하트/Recent 동기화, PC↔모바일 결과를 요청 없이 바꾸지 않는다.
7. **데이터·비용 보호:** PREVIEW/TEST/PRODUCTION 공유 사용자 원본을 변경하거나 초기화하지 않는다. 대량 삭제/백필/변환, 강제 캐시 삭제, 전체 반복 조회 금지. 10만 명 규모에서 변경된 항목만 읽고 쓰는 방식을 검토한다.
8. **실제 상태만 보고:** 분석 완료·로컬 수정·로컬 테스트·GitHub commit/push·독립 감사·실제 배포·실기기 PASS는 각각 다르다. 확인하지 못한 사실은 '미확인'이라고 말한다.
9. **채팅 간 한 기준:** 새로운 채팅은 과거 사용자 설명 대신 GitHub 현재 상태를 읽는다. 한 기능을 여러 AI가 동시에 수정하지 않는다. ChatGPT가 다른 채팅의 Codex 임시 로컬 파일을 볼 수 있다고 주장하지 않는다.
10. **모든 작업 체크리스트와 매일의 루틴:** 일을 시작하기 전에 무엇을 할지 빠짐없이 보고하고, 하루마다 실제 미완료 업무를 기준으로 우선순위를 정한다. 긴급 사고는 먼저 처리한다.

## 2. 이번에 드러난 실패 — 재발 방지

- **합의 누락:** 분석에서는 모두 구현하겠다고 한 내용을 구현 단계에서 일부만 처리하거나 설명 없이 제외함.
- **지시 번복:** app514 PR #512 후속 명령을 짧게/길게/다르게 반복 제시하면서 같은 작업의 최종 기준을 계속 바꿈.
- **작업물 미보존:** app514 P1 수정과 로컬 검사 성공 보고 뒤 GitHub push 실패 및 사용량 소진으로 원격 결과가 없는 상황 발생.
- **상태 과장:** 로컬 검사를 원격 저장, 실제 서버 데이터 확인, 배포로 혼동.
- **맥락 오해:** 사용자의 강한 불만을 단순 정보 요청으로 해석해 불필요한 안내를 함.
- **과도한 절차:** 사용자 목표보다 추가 테스트·새 브랜치·중복 검토 자체를 우선함.

같은 문제가 생기면 사과나 새 장문 지침을 덧붙이는 대신 **현재 GitHub 사실, 빠진 합격 항목, 최소 복구 작업 1개**를 보고한다.

## 3. 승인 후 끝까지 지키는 '작업 계약'

각 기능 착수 전에 아래 7개를 정리해 사용자에게 보여준다.

- **최종 사용자 결과:** 무엇이 언제, 어느 화면에서, 어떤 기기에서 정확히 동작해야 하는가.
- **기능 전체 체크리스트:** 요청된 동작을 누락 없이 분해한다. 화면 즉시 반응 → 저장/동기화 → 재접속 → PC/모바일 → 오류/오프라인 처리까지 해당 기능의 실제 경로를 연결한다.
- **보호선:** 기존 정상 기능, 캐시, 서버 원본, 비용, 환경별 호환성에서 바꾸지 않을 것.
- **허용 수정 범위:** 변경 대상/제외 대상을 명시. 합의한 기능은 사용자 동의 없이 제외할 수 없다.
- **합격 증거:** 기능별 테스트, TypeScript/Build, 필요한 서버·실기기·비용 검증; 자동검사와 실사용 결과 분리.
- **중단 조건:** 데이터 위험, 기존 정상 기능 훼손, 비용 증가, 원격 GitHub 저장 실패, 사용량 소진, 미해결 감사 FAIL.
- **담당과 고정 SHA:** 작업자 1명, 브랜치/기준 커밋, 다음 한 작업, 배포·승격 승인 상태.

**중요:** 사용자가 이 계약을 승인하면 AI가 쉬운 부분만 골라 진행할 권한이 생기는 것이 아니다. 원래 기능 전체가 완료될 때까지 항목별로 추적한다. 완료 못 한 항목은 반드시 미완료로 남긴다.

## 4. 시간·사용량·작업물 보존

1. 시작 시 실제 GitHub HEAD·PR·지난 SHA·기존 검사 결과와 이전 작업환경 복구 가능성을 먼저 확인한다. Codex/Work 잔여 사용량을 볼 수 없으면 미확인으로 표시하고 범위를 작게 정한다.
2. 하루에 우선 처리할 일 하나를 중심으로 필요한 파일·검사만 정한다. 같은 원인을 반복 조사하거나 큰 상태 문서·전체 저장소를 계속 다시 읽지 않는다.
3. **큰 작업은 초기에 복구 가능한 안전 지점의 commit/push부터 확보한다.** 최종 합격 전이면 Draft/WIP·미검증으로 표기한다. 새 전체 검증을 늘리기 전에 원격에 복구 지점이 있어야 한다.
4. 수정 중에는 직접 영향 검사 중심, 최종 후보에서 필수 TypeScript/Build/관련 테스트 1회. 이미 통과한 검사를 대상 SHA와 내용이 동일한 경우 무의미하게 반복하지 않는다.
5. 원격 push/권한 실패를 만나면 다른 기능·분석·대형 감사로 넘어가지 않는다. 먼저 저장 문제를 해결한다. 해결 불가면 로컬 커밋·파일 목록·원격 미저장 상태·재개 방법을 남기고 중단한다.
6. 사용량이 부족해지면 새 조사보다 변경분 보존을 우선한다. 사용량을 직접 볼 수 없을 때는 충분하다고 가정하지 않는다.
7. Codex는 **확정 명령 하나**로 작업하며 중단되면 같은 채팅에서 지점만 이어간다. Work는 **GitHub에 실제 push된 고정 SHA**만 집중 감사한다. 지난 PASS를 이유 없이 재검증하지 않는다.
8. 반복 실패 때는 방법을 즉흥 확대하지 않고 원인·위험·대체안 보고 후 사용자 판단을 받는다.

## 5. 작업마다 빠짐없이 보고할 체크리스트

모든 실제 개발/검증/문서 작업의 **시작·중간·종료 보고**에서 항목을 추적한다. 실제 증거가 없으면 [x] 금지. 단순한 작업은 같은 내용으로 짧게 압축한다.

- [ ] **목표와 최종 사용자 동작** 확정
- [ ] **합의한 세부 기능 전부** 적고 누락·임의 제외 0건 확인
- [ ] **보호할 정상 기능/데이터/비용** 및 작업 범위 확정
- [ ] **담당자/브랜치/정확한 기준 SHA**, 다음 작업 1개 지정
- [ ] **수정과 GitHub 저장** 구분: commit SHA, push/PR 실제 확인
- [ ] **필수 검사** TypeScript/Build/해당 회귀/비용/PC·모바일 결과 표시
- [ ] **독립 감사/배포/실기기/TEST·PRODUCTION** 각각 완료·미완료·승인 상태 표시
- [ ] **당초 계약 전체 충족 여부**와 남은 위험·막힌 이유·다음 작업 기록

**보고 예시:** `목표 | 합의 항목 2/3(1건 미완료) | GitHub SHA 또는 미저장 | 검사 PASS/미검증 | 배포 안 함 | 다음 1건`.
근거 없이 %를 만들지 않는다. 기존 AGENTS.md의 근거 있는 3중 진척도 보고 기준이 적용될 때만 그대로 병기한다.

## 6. 매일의 고정 루틴 — 한국 시간, 긴급 사고 제외

### 하루 시작: 무엇을 해야 하는지 먼저 결정
1. GitHub의 `AGENTS.md`, `CURRENT_RELEASE_STATE.md` 최신 유효 부분, `NEXT_CODEX_TASK.md` 관련 부분, `WORK_AUDIT_CHECKLIST.md`, 이 문서, `preview` 실제 HEAD와 열린 주요 PR 확인. 긴 누적 문서 전체를 매일 읽으며 사용량을 낭비하지 않는다.
2. 전날 중단 작업, **GitHub 미저장 수정**, 감사 FAIL, 실사용 오류·데이터 위험을 먼저 확인한다. 문서와 실제 저장소가 다르면 실제 GitHub 상태를 기준으로 바로잡는다.
3. **오늘 가장 중요한 작업 1개**를 정하고, 필요한 경우에만 다음 후보 1개를 둔다. 작업별 목표·합격선·담당·GitHub 보존 시점·위험을 한눈에 보고한다.

### 낮 동안: 합의한 작업을 완료
4. 계약 체크리스트 공개 → 합의 확정 → 한 작업자가 수정 → 중간 GitHub 보존 → 필수 검사 → 고위험 변경만 독립 감사 → 허용된 환경 확인.
5. 이미 통과한 검사를 중복 반복하지 않고, 합의한 세부 동작을 모두 추적한다. 막히면 임의로 일부를 제외하지 않고 멈춰서 보고한다.
6. 사용자가 배포 금지한 작업은 코드나 문서가 저장돼도 **배포하지 않는다**. TEST/PRODUCTION은 별도 명시 승인.

### 하루 종료: 다음날 재설명 없이 재개
7. GitHub 실제 SHA/PR 상태 재확인. 로컬 전용 작업·업로드 실패·실사용 미검증을 그대로 기록한다.
8. `CURRENT_RELEASE_STATE.md` 또는 그 문서에서 참조하는 최신 짧은 기록에 완료·미완료·정확한 SHA·다음 작업 하나를 갱신한다. 크고 오래된 일지 전체를 재작성하지 않는다.
9. **다음날 시작할 단일 작업과 재개 지시**를 한 번만 정한다. 하루가 바뀌었다는 이유로 설계·명령을 재작성하지 않는다.

### 긴급 예외
실사용자 데이터 손실, 서비스 장애, 인증/보안 사고는 당일 루틴보다 우선한다. 파괴적 사용자 데이터 작업은 긴급 상황이라도 필요한 별도 승인을 받는다.

## 8. 자동 예약의 정확한 의미

- ChatGPT 일정 예약은 예약 시간에 **상태 확인·알림·하루 계획 작성**을 실행할 수 있다.
- 예약만으로 과거 Codex 채팅을 자동으로 열고 미업로드 로컬 커밋을 push할 수는 없다.
- '예약 완료'를 'Codex 자동 실행'으로 말하지 않는다.

**완료의 기준:** 이 문서도 GitHub PR/commit이 실제 확인되기 전에는 저장했다고 보고하지 않는다. 병합되지 않은 문서 PR은 기본 `preview` 작업 규칙으로 이미 발효됐다고 주장하지 않는다.

## 9. 실무형 개발과 선행 코드 정리 판단 — 2026-10-27 디렉터 추가 지시

- 작업 성공에 필요하지 않은 형식적 절차, 중복 검사, 불필요한 코드 정리, 과한 구조 분석은 제거한다. 실제 개발자가 하듯 필요한 작업만 선택하고 빠르게 검증·보존한다.

- 복잡해 보인다는 인상이나 파일 길이만으로 구조 전체를 재작성하거나 정상 코드를 손대지 않는다. 필요한 부분만 정리하고 기존 동작·데이터·비용·기기 동기화는 보존한다.
